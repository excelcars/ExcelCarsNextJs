# Vehicle Master — Existing-System SSOT

## 1. Document Purpose

This document records the observed behavior of the legacy vehicle make/model/variant master implementation in `C:\KhizarShaikh\Project\ExcelCars`. It describes the existing system only; it is not a redesign specification.

## 2. Business Purpose

The vehicle master provides reusable vehicle names for car-entry forms and reports:

- Make, such as `Maruti` or `Honda`.
- Model, such as `Swift` or `City`, associated with a make.
- Variant, such as `VXI` or `ZX`, associated with a make and model.

The master is not exposed as an independent Configuration CRUD screen in the reviewed legacy views. It is populated as a side effect of saving Inventory and Inquiry records, then reused by RTO and other modules for suggestions or dropdowns.

## 3. Database Tables

| Table | Key | Business value | Relationship |
|---|---|---|---|
| `Car_Make_Master` | `PK_Make_ID` | `Make` | Root vehicle level |
| `Car_Model_Master` | `PK_Model_ID` | `Model` | `FK_Make_ID` points to the make |
| `Car_Variant_Master` | `PK_Variant_ID` | `Variant` | `FK_Make_ID` and `FK_Model_ID` identify its make/model |

The generated Entity Framework classes show nullable text, foreign-key, and audit columns. Audit fields are `Created_By`, `Created_Dt`, `Updated_By`, and `Updated_Dt`. The identity keys are generated by the database. The reviewed application code does not show a separate active/inactive flag, delete workflow, or server-side uniqueness constraint.

## 4. Read/Lookup Behavior

### 4.1 Generic autocomplete endpoints

The following public-to-the-controller JSON actions are in `AdminController`:

| Route | Source method | Query behavior |
|---|---|---|
| `/Admin/AutoCompleteMake?term=...` | `Get_Make_AutoComplete` | `Car_Make_Master.Make.StartsWith(term)`; trims and `Distinct`s returned names |
| `/Admin/AutoCompleteModel?term=...` | `Get_Model_AutoComplete` | `Car_Model_Master.Model.StartsWith(term)`; trims and `Distinct`s returned names |
| `/Admin/AutoCompleteVariant?term=...` | `Get_Variant_AutoComplete` | `Car_Variant_Master.Variant.StartsWith(term)`; trims and `Distinct`s returned names |

The generic autocomplete queries do not receive a make or model ID. Consequently, model suggestions are not restricted to the selected make and variant suggestions are not restricted to the selected make/model. Matching is prefix-based, not exact or contains-based. The query does not explicitly sort the values.

These actions have no module-specific `AuthorizeFilter`; the controller's session-expiry behavior still applies. They are used by RTO, Inventory, Insurance, Loan, Follow-up, and report screens.

### 4.2 Dependent Inquiry dropdowns

Inquiry uses separate dependent lookup methods:

- `Get_Car_ModelList(MakeID)` returns models where `FK_Make_ID == MakeID`.
- `Get_Car_VariantList(MakeID, ModelID)` returns variants where both `FK_Make_ID == MakeID` and `FK_Model_ID == ModelID`.

The Inquiry view calls the model endpoint after make selection and the variant endpoint after model selection. These endpoints return IDs and display values through `Car_Make_Master_List`, `Car_Model_Master_List`, and `Car_Variant_Master_List` projection objects.

## 5. How Master Values Are Created

### 5.1 Inventory create/update

`Inventory_Management.Insert_Update_Inventory()` performs this sequence while saving an inventory vehicle:

1. Find a make by exact `Make` text.
2. If not found, create `Car_Make_Master`, set the make text and created audit fields, and save it.
3. Find a model by exact `FK_Make_ID + Model`.
4. If not found, create `Car_Model_Master` with the selected make ID, model text, and audit fields, and save it.
5. Find a variant by exact `FK_Make_ID + FK_Model_ID + Variant`.
6. If not found, create `Car_Variant_Master` with both parent IDs, variant text, and audit fields, and save it.
7. Continue saving the inventory record.

Therefore, a manually typed value in the Inventory create form can become a vehicle-master value when the inventory save succeeds. Existing master rows are reused; they are not duplicated when the exact comparison matches.

The Inventory page and save action are protected by `AuthorizeFilter(DatabaseFunctionname = "Inventory_Management")`.

### 5.2 Inquiry create/update

`Inquiry.InsertUpdateInqiury()` repeats the same make→model→variant insert-if-not-found process for each item in `lst_Inquiry_Details`:

- Make lookup is exact by make text.
- Model lookup is exact by make ID plus model text.
- Variant lookup is exact by make ID, model ID, plus variant text.
- Created and updated audit values are populated from the logged-in `SessionInfo.UserId` and current time.

Thus, saving an Inquiry can also add new values to the vehicle master. The Inquiry screen and `InsertUpdateInquiry` action are protected by `AuthorizeFilter(DatabaseFunctionname = "Inquiry_Management")`.

### 5.3 RTO create/update

RTO does not perform the master upsert. Its save method copies the posted strings directly to:

- `RTO_Agent.Car_Make`
- `RTO_Agent.Car_Model`
- `RTO_Agent.Car_Variant`

So an RTO user can manually enter a value that is not suggested, but saving that RTO record does not add the value to `Car_Make_Master`, `Car_Model_Master`, or `Car_Variant_Master`.

## 6. Update, Delete, And Maintenance

- There is no separate make/model/variant master list page found under `Views\Configuration`.
- No standalone master edit action was found.
- No standalone master delete action was found.
- Existing master rows are effectively updated only through the audit fields during the create-flow upsert; the vehicle text itself is assigned again by the save code.
- Deleting an Inventory, Inquiry, or RTO record does not show a corresponding vehicle-master delete operation in the reviewed code. Master values can therefore remain after the originating transaction is deleted.

## 7. Validation And Edge Cases

- Generic autocomplete only suggests values; it does not enforce selection from the suggestion list.
- RTO, Insurance, Loan, and Follow-up can therefore submit manually typed values without a matching master row.
- The Inventory and Inquiry master-upsert code uses exact string comparisons and does not normalize case or whitespace before lookup. This can allow logically duplicate values when formatting differs.
- The lookup methods trim returned values, but the save comparisons and stored values are based on the submitted text.
- Because the upsert code constructs a new entity before checking whether the input is blank, bypassing client-side required validation may allow blank make/model/variant master rows to be attempted. Database nullability or transaction failure determines the final outcome.
- The generic model and variant autocompletes are global by text and do not enforce parent relationships. A user may see a model or variant that belongs to another make/model.
- There is no explicit ordering, pagination, or active-record filtering in the master lookups.
- If a master lookup throws a database or conversion exception, the caller's normal controller/error handling applies; no dedicated vehicle-master error response was found.

## 8. Cross-Module Usage

The generic make/model/variant suggestions are consumed by:

- RTO Agent Management
- Inventory Management
- Insurance Management
- Loan Management
- Follow-up Management
- Stock Report and Stock Tracking Report screens

Inquiry additionally consumes the ID-based dependent model and variant lists. RTO stores denormalized vehicle text in its own `RTO_Agent` row rather than foreign-key IDs to the vehicle master.
